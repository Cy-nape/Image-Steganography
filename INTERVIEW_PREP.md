## 1. AES-GCM Encryption and Nonce/Salt Handling
**File:** `steganography/crypto.py` (Lines 21-31, 33-55)
```python
def encrypt(plaintext: bytes, passphrase: str) -> bytes:
    salt = os.urandom(16)
    nonce = os.urandom(12)
    key = derive_key(passphrase, salt)
    aesgcm = AESGCM(key)
    ciphertext_with_tag = aesgcm.encrypt(nonce, plaintext, None)
    return salt + nonce + ciphertext_with_tag

def decrypt(blob: bytes, passphrase: str) -> bytes:
    if len(blob) < 44:
        raise DecryptionError("Data blob is too short to be valid ciphertext.")
    
    salt = blob[:16]
    nonce = blob[16:28]
    ciphertext_with_tag = blob[28:]
    
    key = derive_key(passphrase, salt)
    aesgcm = AESGCM(key)
    
    try:
        return aesgcm.decrypt(nonce, ciphertext_with_tag, None)
    except InvalidTag:
        raise DecryptionError("Invalid passphrase or tampered ciphertext")
    # ...
```

* **Q1: How does the encryption function guarantee that the same plaintext and passphrase don't produce the same ciphertext?**
  * **A:** The `encrypt` function generates a fresh 16-byte `salt` and 12-byte `nonce` using `os.urandom()` for every call. The nonce ensures AES-GCM produces unique output, and both are prepended to the ciphertext so the decryptor can read them.
* **Q2: How does the application detect if the encrypted payload has been tampered with?**
  * **A:** It uses `AESGCM(key)`, which is an authenticated encryption mode (AEAD). If a bit is flipped in the image, the authentication tag fails validation. In `decrypt()`, `aesgcm.decrypt()` raises an `InvalidTag` exception, which is caught and mapped to a custom `DecryptionError`.
* **Q3: Why is the blob length checked against exactly 44 bytes in `decrypt()`?**
  * **A:** The blob layout is: 16-byte salt + 12-byte nonce + 16-byte GCM authentication tag. 16+12+16 = 44 bytes. An input shorter than this is physically impossible to be a valid ciphertext generated by this system.
* **Gotcha:** What happens if the `AESGCM` initialization fails or throws a completely unexpected error during decryption?
  * **A:** The `decrypt()` function includes a broad `except Exception as e:` block that catches any other errors and re-raises them as a `DecryptionError` to prevent leaking raw cryptography library internals to the API layer.

## 2. PBKDF2 Key Derivation
**File:** `steganography/crypto.py` (Lines 11-19)
```python
def derive_key(passphrase: str, salt: bytes) -> bytes:
    """Derive a 32-byte key using PBKDF2-HMAC-SHA256."""
    kdf = PBKDF2HMAC(
        algorithm=hashes.SHA256(),
        length=32,
        salt=salt,
        iterations=100000,
    )
    return kdf.derive(passphrase.encode('utf-8'))
```

* **Q1: What algorithm and parameters are used to turn the user's string passphrase into an AES key?**
  * **A:** `PBKDF2HMAC` is used with the `SHA256` hash algorithm, a randomly generated 16-byte salt, and exactly 100,000 iterations to produce a 32-byte (256-bit) key.
* **Q2: How is the salt handled so the decrypt function can recreate the exact same key?**
  * **A:** The `encrypt` function randomly generates the salt, uses it in `derive_key`, and then prepends it in plaintext to the output blob. The `decrypt` function reads the first 16 bytes of the blob to retrieve the salt before calling `derive_key`.
* **Q3: Why use PBKDF2 with 100,000 iterations instead of just hashing the passphrase once with SHA256?**
  * **A:** Iteration stretching (key stretching) slows down brute-force attacks. Hashing once is so fast that an attacker could guess millions of passwords per second. 100,000 iterations forces the attacker's hardware to perform 100,000 operations per single guess.
* **Gotcha:** The `derive_key` function takes a `str` passphrase but `kdf.derive()` requires bytes. How is this handled?
  * **A:** The passphrase string is explicitly encoded to bytes using `passphrase.encode('utf-8')` before being passed to the derivation function.

## 3. LSB Bit Embedding and Capacity Calculation
**File:** `steganography/lsb.py` (Lines 31-52)
```python
        # Check if image has enough capacity (flag: 8 bits, length: 32 bits)
        if len(binary_message) + 40 > img_array.size:
            raise ValueError("Message too large for this image")
        # ...
        # Encode flag
        for i, bit in enumerate(flag_bits):
            flat_image[i] = set_lsb(flat_image[i], int(bit))

            flat_image[i + 8] = set_lsb(flat_image[i + 8], int(bit))
        
        # Encode message
        for i, bit in enumerate(binary_message):
            flat_image[i + 40] = set_lsb(flat_image[i + 40], int(bit))
```
* **Q1: How does the application verify that an image can hold the message before attempting to encode?**
  * **A:** It calculates `len(binary_message) + 40` and checks if it is strictly greater than `img_array.size` (which represents the total number of color channels available in the flattened image array).
* **Q2: What does the "40" represent in the capacity calculation?**
  * **A:** It represents the 40-bit metadata header overhead: an 8-bit `pipeline_flag` followed by a 32-bit `message_length`.
* **Q3: How is a single bit of the message mathematically embedded into a pixel's color channel?**
  * **A:** The `set_lsb(value, bit)` function uses bitwise operations. If `bit == 1`, it uses `value | 1` to force the Least Significant Bit to 1. If `bit == 0`, it uses `value & 0xFE` (11111110) to clear the LSB to 0.
* **Gotcha:** What happens if `binary_message` is empty?
  * **A:** The `lsb_encode` function explicitly checks `if not binary_message:` and raises a `ValueError("Empty binary message provided")` before modifying any pixels.

## 4. Huffman Compression
**File:** `steganography/huffman.py` (Lines 28-45, 94-98)
```python
            # Build Huffman tree
            while len(heap) > 1:
                lo = heapq.heappop(heap)
                hi = heapq.heappop(heap)
                # ...
                heapq.heappush(heap, [lo[0] + hi[0]] + lo[1:] + hi[1:])

            # Generate final encoding dictionary
            self.huffman_dict = {a[0]: a[1] for a in heapq.heappop(heap)[1:]}
```
* **Q1: What core data structure is used to build the Huffman tree?**
  * **A:** A min-heap (`heapq`) initialized with a list of nodes formatted as `[weight, [char, ""]]`.
* **Q2: How are the binary codes assigned to characters during tree building?**
  * **A:** As the two lowest-weight nodes (`lo` and `hi`) are popped from the heap, a '0' is prepended to the binary code of all characters in the `lo` subtree, and a '1' is prepended to the code of all characters in the `hi` subtree.
* **Q3: How does the decoder know when a character code is complete without delimiters?**
  * **A:** Huffman codes are prefix-free. The `decode()` method iterates bit-by-bit, appending to a `temp_code`. As soon as `temp_code` matches a key in the `reverse_dict`, it maps it to the character and resets `temp_code`.
* **Gotcha:** The Huffman dictionary isn't embedded in the image pixels. How does the decoder recover it?
  * **A:** It is stored in the relational database as a JSON object inside the `EncodeJob` model, keyed by the SHA256 `file_hash` of the output image.

## 5. Pipeline Flag Design & Self-Describing Format
**File:** `steganography/utils.py` (Lines 26-51)
```python
        if pipeline == 'secure':
            # Prepend 32-bit length header to handle padding
            bit_length = len(binary_message)
            bit_length_str = format(bit_length, '032b')
            binary_message_with_length = bit_length_str + binary_message
            
            # Pad to multiple of 8 bits
            padded_binary_message = binary_message_with_length
            if len(padded_binary_message) % 8 != 0:
                padded_binary_message = padded_binary_message.ljust(len(padded_binary_message) + (8 - len(padded_binary_message) % 8), '0')
            # ... encryption ...
            pipeline_flag = 1
```
* **Q1: How does the decoder know whether an image was encoded using the basic or secure pipeline?**
  * **A:** The first 8 bits of the LSB payload contain a `pipeline_flag` (0 for basic, 1 for secure). `lsb_decode` extracts this globally first.
* **Q2: In the secure pipeline, how is the message prepared before encryption?**
  * **A:** A 32-bit string representing the original bit length is prepended to the compressed binary message. The combined string is then right-padded with '0's until its length is a multiple of 8, converting it cleanly into bytes for AES.
* **Q3: Why is the `message_length` stored by `lsb_encode` different from the original message length in the secure pipeline?**
  * **A:** In the secure pipeline, the `message_length` passed to `lsb_encode` is the length of the final *ciphertext string* (which includes the AES salt, nonce, and tag overhead), not the original plaintext message.
* **Gotcha:** How does the secure pipeline recover the exact length of the original Huffman binary string after decrypting the padded block?
  * **A:** Because a 32-bit length header was prepended *before* encryption/padding, the decoder reads the first 32 bits of the decrypted plaintext to get the exact `bit_length`, then slices the payload using `huffman_binary = padded_binary_message[32:32+bit_length]`.

## 6. JWT Authentication Flow


* **Q1: Where does the API middleware look for the JWT token?**
  * **A:** It checks the `Authorization` header for a string starting with `Bearer `, splitting it to extract the token payload.
* **Q2: How does the application verify the token hasn't been tampered with?**
  * **A:** It uses `jwt.decode(token, current_app.config['SECRET_KEY'], algorithms=["HS256"])`. This uses the server's private `SECRET_KEY` to verify the HMAC-SHA256 signature attached to the token.
* **Q3: If the token is valid, how is the user's identity made available to the Flask route handler?**
  * **A:** The user ID is extracted from the token's payload (`data['user_id']`), the `User` record is fetched from the database, and it is attached to the Flask global context as `g.user`.
* **Gotcha:** What happens if a perfectly valid, unexpired token is presented, but the user has been deleted from the database?
  * **A:** `User.query.get(data['user_id'])` returns `None`, and the decorator safely catches this and returns a 401 error `{'error': 'User not found!'}` instead of throwing an internal server error.

## 7. API Key Hashing and Revocation
**File:** `api_keys.py` (Lines 16-28, 64-66)
```python
    # Generate a cryptographically secure 32-byte hex string (64 characters)
    raw_key = secrets.token_hex(32)
    # Hash for storage
    key_hash = hashlib.sha256(raw_key.encode('utf-8')).hexdigest()
    # Prefix for display
    key_prefix = raw_key[:8]
```
* **Q1: How is the raw API key generated and stored to prevent leaks if the database is compromised?**
  * **A:** A raw 32-byte hex string is generated using `secrets.token_hex(32)`. The database only stores a SHA256 hash of this raw key (`key_hash`). The raw plaintext key is returned to the user only once upon creation.
* **Q2: If only the hash is stored, how is the API key identified in the UI list?**
  * **A:** A `key_prefix` consisting of the first 8 characters of the raw key is stored in plaintext alongside the hash, allowing users to identify their keys visually without revealing the full secret.
* **Q3: How does the revocation mechanism work?**
  * **A:** It uses a "soft delete" pattern. Instead of removing the row from the database, the `is_active` boolean column is set to `False`. The authentication middleware only accepts keys where `is_active=True`.
* **Gotcha:** If an attacker guesses a valid `key_id`, can they delete other users' keys via the API?
  * **A:** No. The `revoke_api_key` route specifically filters by `id=key_id` AND `user_id=g.user.id`, ensuring logged-in users can only revoke their own keys.

  * **A:** Extensions can be easily spoofed (e.g., a malware executable renamed to `.png`). The PIL `verify()` method parses the file headers to confirm it's actually a valid image format before the steganography pipeline processes it.
* **Q3: How is the output image delivered without leaving files on the server's disk?**
  * **A:** The encoded image is written to an in-memory `io.BytesIO()` buffer using the `output_path=output_buffer` argument, and sent directly to the client using `send_file(output_buffer)`.
* **Gotcha:** What guarantees the temporary input file is deleted even if an exception occurs during encoding?
  * **A:** A `finally:` block checks if `temp_input` exists and unconditionally calls `os.remove(temp_input)`, preventing disk space leaks on failures.

## 9. Walk Me Through This Project (90-Second Script)
"This is a Flask-based Image Steganography API backed by an SQLite database via SQLAlchemy. When a user uploads an image and a secret message, the application first validates the file using PIL to ensure it's a genuine image, saving it temporarily to disk. 

The payload enters a dynamic orchestration pipeline (`utils.py`). First, the message is compressed using a custom **Huffman coding** algorithm to save space. If the user selected the **Secure Pipeline**, we derive a 32-byte key from their passphrase using **PBKDF2 (100,000 iterations, SHA256)** with a fresh salt. The compressed message is padded and encrypted using **AES-256-GCM**, returning an authenticated ciphertext blob.

We then construct a 40-bit metadata header—an 8-bit pipeline flag (basic vs secure) and a 32-bit payload length. The `lsb.py` module mathematically embeds this header followed by the binary payload into the Least Significant Bits of the flattened image array. 

The final modified image is written directly to an in-memory `BytesIO` buffer and streamed back to the user, ensuring zero artifacts are left on our disk. Because the Huffman decoding dictionary is required to read the message later, we store it as JSON in the database, uniquely keyed to the SHA256 hash of the *output* image. 

The API is secured via a dual-auth system supporting both **JWT Bearer tokens** for web sessions and hashed **API Keys** for programmatic access. Revoked keys use a soft-delete pattern (`is_active=False`) so audit history is preserved."

## Current Known Limitations
* **Stateless Decoding Flaw:** Because the Huffman dictionary is stored in the local SQLite database and keyed by the output file hash, an encoded image *cannot* be decoded if it is uploaded to a different instance of the application, or if the image is resized/compressed (which alters its SHA256 hash).
* **Format Fragility:** Steganography via LSB is extremely fragile. Uploading the resulting PNG to a service like WhatsApp, Facebook, or Twitter will strip the payload entirely due to lossy JPEG/WebP compression.
* **Capacity Constraints:** The LSB method limits data capacity to exactly 1 bit per color channel pixel (roughly ~375KB payload max on a 1MB image).
* **RGBA Processing:** To prevent transparency bits from being corrupted by LSB embedding, the core API `lsb.py` explicitly standardizes all incoming images to RGB via `.convert('RGB')` prior to array conversion. While this prevents visual artifacts, it deliberately strips any existing alpha channel (transparency) from the output image.
* **Denial of Service (DoS):** While rate limiting exists, the API processes image decoding synchronously. Submitting heavily crafted or massive images could tie up worker threads, resulting in DoS.
